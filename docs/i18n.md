# Translating the Android launcher

The launcher (android/app) shows its texts in English, Turkish (tr), Brazilian Portuguese (pt-BR) and Latin American Spanish (es-419). English is the source and the fallback: a text a language lacks shows in English. This page is for engineers who move texts out of the Java and for translators.

Game logs, logcat lines, the readiness report and everything the Python packer or the native host prints stay English: users attach them to issues, and code parses some of them.

## Where texts live

All texts are Android string resources, one file per area:

| Folder | Language |
|---|---|
| `android/app/src/main/res/values/` | English (the source; `res/resources.properties` names it en-US) |
| `values-tr/` | Türkçe |
| `values-pt-rBR/` | Português (Brasil) |
| `values-b+es+419/` | Español (Latinoamérica). Android uses it for es-MX, es-AR, es-CO and the other Latin American Spanish locales. Spain's es-ES falls back to English. |

Each folder has the same files, one per area. Each area's Java files have exactly one owner, the area; during phase 1 (moving the texts, eight packages in parallel) a package edits only its own Java files, its own `strings_<area>.xml` in the four folders and its own `dm/tools/tests/i18n_ratchet/<area>.tsv`. Java files are in `android/app/src/main/java/dev/nxnative/android/` unless marked *ondevice* (`android/app/src/ondevice/java/dev/nxnative/android/`).

| File | Area | Java files |
|---|---|---|
| `strings_common.xml` | words used everywhere | closed: nobody adds to it while the areas are being moved; put a word you need in your own area's file (duplicates across areas are fine) |
| `strings_home.xml` | home | MainActivity, Ui, Prefs, FrontendLaunch, HomeLabels |
| `strings_prepare.xml` | prepare | Ondevice, Job, PackService, DumpCheck, PrepareErrors, Eta (all *ondevice*) |
| `strings_readiness.xml` | readiness | Readiness, ReadinessActivity |
| `strings_game.xml` | game | GameActivity (all of it, its start-up readiness notice and its Details included), SidePanel, TouchControls, Overlay, Fsr, Lsfg, SelftestActivity |
| `strings_saves.xml` | saves | SaveUi, SaveStore, SaveMigrate |
| `strings_packs.xml` | packs | PackUi, Pack, PackZip, PackFind, PackCheck, BuildCheck, DumpLayout, RomfsCheck, Nup, ShaderLibs, RewriteKey |
| `strings_settings.xml` | settings | GameSettings, Folders, GpuDriver, DriverFetch, DriverZip, Updater, UpdateCheck, ReleaseNotes, MemText, Signer, Profile, Lang |
| `strings_errors.xml` | errors | JobErrors (new, *ondevice*): the packer's error codes ([Errors of the packer](#errors-of-the-packer)) |

The other Java files have no area:

- **Closed** (the texts' machinery; send a needed change to the integrator): Tr, TrAndroid, Msg, LocalizedIOException, App, and Lang, whose keys (`settings_language_*`) live in `strings_settings.xml` (its ratchet is settings'). The home screen draws the Language row with `Lang.title()` and `Lang.label()`.
- **English by rule**: Zstd, Native, LogProvider, and *ondevice* Outputs, PackEngine, FakeEngine, ShaderResults. They are failure details that reach the screen only after a translated sentence ("Cannot use X: *detail*"), or a test engine.
- **No text a user sees**: AppStorage, BananaBackgroundView, Frontend, Game (a log line only), GameList, PathUtil, Streams.

A file in no area must keep a ratchet count of 0 ([Tests](#tests)).

## Keys

- A key is `<area>_<words>`, lower case, words joined by `_`: `home_access_title`, `prepare_cannot_use`, `settings_profile_update`. The first word is the file's area. `test_android_i18n.py` enforces both rules, so two areas can never add the same key.
- Name a key after what the text is, not after its English words: `saves_backup_done_title`, not `saves_saves_backed_up`. Then the English can change without renaming the key.
- A plural is a `<plurals>` resource with the same naming.
- Names that are never translated (the language names in their own language) get `translatable="false"` and live only in `values/`.
- Readiness requirements: see [Readiness requirements](#readiness-requirements).

## Which call where

| Where the text is built | Call |
|---|---|
| A class with a Context (activities, Ui helpers, dialogs, PackService) | `c.getString(R.string.key)`, `c.getString(R.string.key, a, b)`, `c.getResources().getQuantityString(R.plurals.key, n, n)` |
| A class without Android (the JVM tests compile it on its own: BuildCheck, Pack, Profile, SaveStore, Readiness and the rest) | `Tr.s("key", args...)`, `Tr.p("key", n, args...)` |
| A text shown on the screen and also written to a log, a report or job.json | a `Msg`: `new Msg("key", args...)`, `Msg.plural("key", n, args...)`. The screen calls `msg.text()`, the report `msg.english()`. `toString()` is English. A `Msg` passed as an argument of another `Msg`, `Tr.s` or `Tr.english` renders in that text's language; `getString` cannot do that, so pass it `msg.text()`. |
| An exception whose message the user should read in their language | `throw new LocalizedIOException("key", args...)`. `getMessage()` is English (logs, job.json, tests), `getLocalizedMessage()` is the user's language. A `Msg` already built (another area's, a variable declared `Msg` in the same file) is thrown as it is with `new LocalizedIOException(msg, cause)` (`cause` may be null). |
| Showing any exception on the screen | `e.getLocalizedMessage()`, never `e.getMessage()`. For other exceptions it is the same text. |
| A log line, the readiness report, anything parsed back | English: `Tr.english("key", ...)`, `Tr.englishP(...)`, `msg.english()`, or a literal that stays English. Mark such a literal `// i18n-keep` when the ratchet counts it. |
| Dialog OK and Cancel buttons | `android.R.string.ok` and `android.R.string.cancel`. Android translates them, and the English is the same. |
| A list of labels (an array) or a table from a value to its text | a key table: `static final String[] KEYS = {"home_window_1080p", ...}` in the same file, then `Tr.s(KEYS[i])` or `c.getString` of an `int[]` of `R.string` ids. See [Label arrays and fact tables](#label-arrays-and-fact-tables). |

**`Tr.s` or a `Msg`?** Ask first: *does this text ever reach a log, a report, job.json or anything pasted into an issue, now or through a caller?* If it does, it is a `Msg` (or a `LocalizedIOException`), so each place renders it in its own language. Only a text that never leaves the screen is `Tr.s`. The known case: `Profile.versionName()` was `Tr.s`, but BuildCheck, DumpLayout and PackService put it into sentences that also go to job.json and a log line, so a Turkish user got Turkish inside English logs. It is now `Profile.versionMsg()` (a `Msg`), with `versionName()` its English.

`App` installs Tr's Android backend (`TrAndroid`) in every process (main, `:game`, `:selftest`, `:readiness`, `:pack`) before any provider, activity or service starts. On the JVM, `Tr` reads `values/strings_*.xml` from the folder the system property `nx.tr.res` names. Every JVM test passes `TR_RES` and compiles the `TR` sources (`Tr.java`, `Msg.java`, `LocalizedIOException.java`), so the English the tests see is the English the app shows.

A key that does not exist throws `MissingResourceException`. `test_android_i18n.py` checks that every key named in the Java (`Tr.*`, `Msg`, `LocalizedIOException`, `R.string`, `R.plurals`) exists in `values/`, with the right type.

### A missing key in a shipped build

The test suite is the guard, not the app. On the JVM and in a debuggable build (the test app, a debug build) a missing key, a format that does not fit its arguments or any other error of a text lookup through `Tr` or `Msg` throws, so developers and tests see it at once. A shipped (non-debuggable) build installs `Tr.Lenient` around `TrAndroid` (`App`, `Tr.forBuild`): it writes one error line to logcat naming the key and the error (`[RED] text string <key> (<language>): …`, once per key and language in a process), and shows the key's English instead, formatted; if that fails too, the English as written; if the key has no English at all, the key itself. That only keeps the user's screen alive: a text that hits it is a bug that `test_android_i18n.py` should have caught, so fix the text or the test. `TrJvmTest` covers this decision. `c.getString(R.string.x, …)` calls in classes with a Context do not go through `Tr`: a missing `R.string` id fails the build, but a bad format there still throws in every build, so only the placeholder checks of the test guard them.

### Texts that cross areas

A text one area makes and another area puts inside its own sentence belongs to the area that makes it. The owner returns it as a `Msg` (or a String in the user's language when it is only ever shown), and the consumer passes it as an argument of its own key. A consumer never reads another area's key (`test_keys_of_own_area` in `test_android_i18n.py` fails on one), and an area never changes the signature of a method another area calls: it changes what the method returns, or adds a new method beside it.

### References to other labels

A sentence that names a button, a row or a menu of another screen ("Settings › GPU driver", "its in-game panel › Stop the game", "Back up saves makes one", "Tap Retry") takes that label as an argument, from the one resource the screen draws it with. A translator then translates each label once, and the sentence names the button as the user sees it. The label's area gives it through a small accessor that returns a `Msg`; the sentence's area passes `msg.text()` to `getString`, or the `Msg` itself to a `Msg`, `Tr.s` or a `LocalizedIOException`:

| Label | Accessor (area) |
|---|---|
| Settings; Settings › GPU driver, Readiness check, Share log, Folders; the System value of the GPU driver row | `HomeLabels.settings()`, `gpuDriver()`, `readinessCheck()`, `shareLog()`, `folders()`, `gpuSystem()` (home) |
| Add game; a card's Prepare shaders; the Manage sheet's Game settings, Back up saves, Restore saves, Prepare again, Export pack…, Import pack… | `HomeLabels.addGame()`, `prepareShaders()`, `gameSettings()`, `backUpSaves()`, `restoreSaves()`, `prepareAgain()`, `exportPack()`, `importPack()` (home) |
| Stop the game (the in-game panel) | `SidePanel.stopLabel()` (game) |
| Manage (the Preparing card's ⋯) | `Ondevice.manageLabel()` (prepare) |
| System (the phone's own driver) in the GPU driver list | `GpuDriver.systemLabel()` (settings) |

A sentence of the label's own area takes it the same way, from its own key (`home_play`, `prepare_button_retry`). Punctuation the sentence adds stays in the sentence: "with %4$s…." keeps the old "Restore saves…." while the row is "Restore saves". Not labels: the feature's name Prepare used as a noun or a verb ("a dump Prepare can start from", "Dump that build and Prepare it"), which follows the glossary; Android's own names ("Install unknown apps", All files access), which follow the phone's wording; and Back, the phone's back gesture.

`Ui` (home) is used by every area: home moves the words Ui adds itself (its OK, Back and Cancel buttons, ": tap for details") into `strings_home.xml` and keeps Ui's method signatures; the other areas pass their own texts to Ui's helpers and never edit Ui.

"Switches after both merge": the consumer's package leaves that call as it is (its sentence may move, with the producer's English String as the argument), and the integrator makes the one-line switch after merging both. A package that finds another such case lists it in its pull request, the same way.

### Label arrays and fact tables

A key is a string literal directly in the call, so the test can check it exists. The one other form is a **key table**: a `static final String[]` in the same file whose every element is a string literal, none of whose elements is ever assigned and whose name is used only as `KEYS[i]` or `KEYS.length` (no local of the same name, no alias, no `Arrays.fill`), indexed right in the call: `Tr.s(WINDOW_KEYS[i])`, `new Msg(KEYS[k], arg)`. `test_android_i18n.py` then checks every element of the table exists, with the call's type. A table of another class (`Prefs.KEYS[i]`), a two-level table, a key with more glued on (`KEYS[i] + "_short"`) and any key built at run time are refused. A table that maps values to keys is two tables at the same index, as `Readiness.REQ_FACTS` and `REQ_KEYS`; a JVM test checks they pair up.

### Readiness requirements

The host's requirement rows (`Readiness.HOST`) get their title and why through the key table `Readiness.REQ_FACTS` → `REQ_KEYS`: the row of fact `feature.timelineSemaphore` reads `readiness_req_feature_timeline_semaphore`. The key is `readiness_req_` and the fact in lower case words (dots and capitals become `_`), and its English is the HOST row's text word for word (`ReadinessJvmTest` checks it). When two HOST rows check the same fact (Android 12 or newer, `android.sdk` 31, and the warning Android 13 or newer, `android.sdk` 33), the later row's table fact is `fact>=min` (`android.sdk>=33`), which a row matches before its bare fact, and its key ends in the minimum: `readiness_req_android_sdk_33`. In every language it keeps the form `title: why`, because `Readiness.Req` splits on `": "`. A host row the table does not know shows the English it was written with. `Req.shown()`, `shownTitle()` and `shownWhy()` are the screen's text, `english()`, `title` and `why` the report's.

A row's message on the screen is one whole-sentence resource of `Readiness.REQ_MSG_KEYS` (`readiness_row_met`, `_lacks`, `_lacks_bare`, `_degraded`, `_degraded_bare`): the row's why as written (`Req.shownWhy()`, in the language of the moment, no letter upper-cased) after a colon, then the fact's name (`readiness_row_fact_*`, or the fact key and a colon), what the phone reports (`readiness_row_not_reported`, `readiness_row_reports`) and the minimum. A row without a why takes the `_bare` form. The report and the log keep the English message the check always had (`Check.message`, whose why is upper-cased: English only).

Rows from a game's own `readiness.tsv` (`dm/games/<id>/readiness.tsv`, `Readiness.parseReqs`) have no resource and stay English, also when their fact is in the table: their title is English, and their why is English inside the translated sentence. That is why the why always comes after a colon: an English clause there reads as a quoted reason. **Rule:** a resource that takes text which may stay English (a game's row, a tool's `[RED]` line, Android's own description, an exception's detail) puts it after a colon or in parentheses, never into the grammar of the sentence. A translated per-game row needs a `readiness.<lang>.tsv` beside it and build.gradle support for it; neither exists yet.

The fact `unchecked` (nobody answered the GPU check) is report data and stays English. The screen shows its reason by a code (`Readiness.uncheckedCode`, `uncheckedReason`): `no_host` (`readiness_unchecked_no_host`), `timeout` (`readiness_unchecked_timeout`, written by `Readiness.uncheckedTimeout`), or `other`, the host loader's English detail as written, in parentheses.

### Errors of the packer

The packer's errors are English sentences in job.json's `error`. For the failures a user can fix (dump incomplete, wrong build, wrong title, not enough space, unreadable file, out of memory, translator crashed), the packer also prints a code, with this interface (the codes and what reads them: [android/README.md, Error codes](../android/README.md#error-codes)):

- The Python packer prints, before the failure's `[RED]` line, one line `error: <code>` followed by its arguments, each after a tab. A code is lower case words joined by `_`.
- `JobErrors` (*ondevice*, no Android classes): `static String[] parse(String line)` returns `{code, arg...}` for such a line, else null; `static Msg message(String code, String[] args)` returns the code's text, key `errors_<code>` through a key table, or null for a code it does not know.
- job.json gets `error_code` (a string, "" for none) and `error_args` (an array of strings) beside the English `error`, written by PackService; `Job` shows `JobErrors.message(...)` when it knows the code, else the English `error`.

`JobErrors.Watch` picks the `error:` line right before the step's last `[RED]` line out of the step's log; `Job.statusMsg` shows the code's text through `prepare_status_failed_coded` and the notification `Job.errorText()`. Nothing may follow the `[RED]` line: a failed tool's log tail goes before the `error:` line (`pack_errors.Coded(..., detail=lines)`, which `pack_errors.fail` prints first), since a `[RED]` line in a tail printed after the sentence would unpair the code.

### Errors of Prepare

The failures Prepare makes itself, which no packer prints a code for, have codes of their own (`PrepareErrors`, *ondevice*, no Android classes): `step_killed`, `dump_changed`, `tool_exit`, `tool_exit_red`, `compare_failed`, `shader_map`, `dump_free_unknown`, `dump_space`, `dump_not_writable`, and PackService's room check of the app's own storage before the shaders step, `results_free_unknown` and `results_space`. PackService and DumpCheck store the code and its arguments in job.json's `error_code` and `error_args` (the packer's fields) beside the English `error`. `Job.errorMsg` asks `PrepareErrors.message` first, then `JobErrors.message`. The status line puts a phrase (`prepare_error_*`) into `prepare_status_failed` and DumpCheck's whole sentences (`prepare_dump_*`) into `prepare_status_failed_sentence`. A job.json without the fields, or with a code or an argument this build does not read, shows its English `error`. Not coded: DumpLayout's refusals at the identify step (English in job.json), the shader steps' failures inside `shader_split.py` and `vk_android_build.py` (their `[RED]` line is the English detail of `tool_exit_red`; a code there would change a `DMSH_VK_CHAIN` input), and an unexpected exception.

## Writing a text

- **One resource per whole sentence.** Never glue fragments (`"Cannot use " + dir + ": " + why`). Write `Cannot use %1$s: %2$s`. Word order differs: Turkish puts the verb last ("%1$s kullanılamıyor: %2$s").
- **Positional arguments only:** `%1$s`, `%2$d`. A bare `%s` fails the test. Each translation uses exactly the same arguments as the English, in any order.
- **`%s` for anything that was concatenated before** (paths, names, doubles), and `%d` only for whole numbers. `%d` never groups digits (no `%,d` unless the English already had it), so English output stays the same.
- **A literal percent sign:** `%%` in a text that has arguments. A text without arguments is shown as written, so a lone `%` stays `%`.
- **No possessive after a runtime name.** Don't write `%1$s's save`. Turkish needs a suffix that depends on the name ("Zelda'nın", "Kong'un"), and Portuguese and Spanish reorder the phrase. Use a label form: `Save: %1$s`, or `Backing up the save of %1$s…`.
- **No case change of a translated text.** Never `toLowerCase` or `toUpperCase` a resource and put it inside a sentence. `Locale.ROOT` breaks Turkish İ and ı, and the other languages capitalize differently. Write a separate resource for the form you need.
- **Plurals for counts:** `<plurals>` with `one` and `other` in English (`other` is required). Turkish uses no plural after a number ("3 oyun"), so its `one` and `other` can be the same text. Pass the number twice when the text shows it: `getQuantityString(R.plurals.x, n, n)`, `Tr.p("x", n, n)`.
- **References to other labels** ("Settings › GPU driver", "Tap Retry") take the label from its own resource as an argument, so they match the translated button ([References to other labels](#references-to-other-labels)).
- **Text that may stay English** inside a translated sentence (a game's readiness row, a tool's line, an exception's detail) goes after a colon or in parentheses, never into the sentence's grammar.
- **Numbers on screen:** in the app's language, not the system's. Put the number into the resource (`%1$.1f MB`, `%1$d minutes ago`) and let the resource format it: Android's `getString` and `Tr` format in the language of the text's resources. Never `DateUtils` or `String.format(Locale.US / ROOT)` for a number a translated text shows. Logs and reports keep English (`Msg.english()`, `Locale.ROOT`). Sizes are `SaveStore.sizeMsg`, relative times `Readiness.ago`. What a user sees: with the app in English, Turkish, Portuguese or Spanish, numbers and units follow that language ("1,2 MB" in Turkish). With a system language the app has no texts for (German, say) and the app on System default, the texts are English and the numbers are formatted the system language's way inside them ("1,2 MB", the same as Android does for any app); picking English in Settings › Language makes them "1.2 MB".
- **Native digits:** Android formats `%d` with the resource configuration's locale. A user whose system language we do not ship but which writes its own digits (Arabic, Persian, some Indic languages) sees those digits inside the English texts (for example the readiness summary's count). This is accepted. Where Latin digits matter (an ID, a version, a size someone types back), pass a String made with `Locale.ROOT` as `%1$s`.
- **Escaping (aapt2):** write `'` as `\'` and `"` as `\"`, and a leading `@` or `?` as `\@` or `\?`. A newline is `\n`. Runs of spaces collapse to one unless the text is inside double quotes. Turkish uses `'` before suffixes ("shader\'lar", "Vulkan\'ı"). The test fails on an unescaped `'` or `"`.
- **Plain text only:** no `<b>`, `<xliff:g>` or other markup inside a string.
- **English output stays byte-identical** when a text moves. If you rephrase on purpose (a possessive, a plural that was wrong in English), list the changed English sentences in the commit message, so the docs and `docs/agents/symptoms.md` can follow.

## Language choice

Settings › Language offers System default, English, Türkçe, Português (Brasil) and Español (Latinoamérica) (`Lang.java`).

- **Android 13 and newer:** Android's per-app language (`LocaleManager`). It is the same setting as the system's Settings › Apps › Anka Native › Language. That page lists the languages from the localeConfig that the build generates (`generateLocaleConfig` in `build.gradle`, from `res/resources.properties` and the `values-*` folders). Android keeps the choice and applies it to every process of the app.
- **Android 12 (API 31, 32):** no per-app language, and the app has no AndroidX dependency (AppCompat would do the same through `AppCompatDelegate`). The choice is stored in `files/app_locale.txt`. Each activity and PackService wrap their context in it (`attachBaseContext` → `Lang.wrap`), and `TrAndroid` reads it. A process that is already running (a game, a Prepare job) keeps its language until it starts again.
- GameActivity and SelftestActivity list `locale|layoutDirection` in their `configChanges`, so a language change never restarts a running game. Their panels pick up the new language the next time they open. MainActivity and ReadinessActivity are recreated and draw themselves again.

**Pseudo-locales** are on in every build except the public release (`pseudoLocalesEnabled`). Turn on Developer options, then pick English (XA) (accented and longer) or ar-XB (right to left) as the phone's language. A text still hard-coded in the Java stays plain English, and a label that is too long gets cut.

## Tests

```sh
python3 dm/tools/tests/test_android_i18n.py                    # the rules, the ratchet, Tr on the JVM
python3 dm/tools/tests/test_android_i18n.py --list Ondevice.java   # what the ratchet still counts in a file, with line numbers
python3 dm/tools/tests/test_android_i18n.py --ratchet prepare      # write the area's current counts (it only goes down)
python3 dm/tools/tests/test_android_i18n.py --rebaseline packs "merge of work/resolution" [New.java ...]   # the integrator's, after a merge (below)
```

Run the JVM tests with JDK 21 first on `PATH` ([android/TESTING.md](../android/TESTING.md#1-build-what-goes-to-the-phone)).

`test_android_i18n.py` checks:

- every strings file is well-formed XML;
- `values/` has exactly the `strings_<area>.xml` files, and each translation folder has the same ones;
- keys are named after their area;
- every key in a translation exists in the same English file;
- each string has the same arguments as its English;
- plurals have `other`;
- `'` and `"` are escaped;
- `translatable="false"` texts are not translated;
- readiness requirements keep `": "`;
- every key the Java names exists;
- every key is a string literal directly in the call (`Tr.s("key", ...)`, never `"readiness_req_" + fact`) or a key table of literals in the same file (`Tr.s(KEYS[i])`), so the check above sees it;
- a Java file names only its own area's keys and `common_` (`test_keys_of_own_area`; its area is the ratchet tsv that lists it);
- Tr's XML backend matches aapt2 (TrJvmTest).

It prints each language's completeness without failing.

Each area also has a JVM test that renders its texts with the arguments the Java passes and compares the English with what the code wrote before (`test_android_home_texts`, `_prepare_texts`, `_prepare_errors`, `_readiness_i18n`, `_game_texts`, `_saves_text`, `_settings_texts`, `_joberrors`, and `test_pack_errors` for the packer's side). A label passed as an argument is rendered through its accessor there (`HomeLabels`), so a test fails when a sentence's English drifts from the label.

**The ratchet** (`dm/tools/tests/i18n_ratchet/<area>.tsv`) counts, per Java file, the literals that read as text shown to a user. A count may never grow. A file that is in no area's list must have none. When you move texts out of a file, run `--ratchet <area>` and commit the lower count. Lines that must stay English and that the counter still picks up (a report line, a technical name) get a `// i18n-keep` comment.

**After a merge** (the integrator): the counts were taken on work/next, and a branch merged in later (a review fix of android12, frontend-launch or resolution, or a phase 1 package that crossed another's change) can bring new English literals into a counted file, so the ratchet fails after the merge. Settle it once per merge and area, in its own commit right after the merge commit: either move the new literals to the area's strings file (the normal way while that area's package is not running), or, when the area's package is running or the texts must wait, run `--rebaseline <area> "merge of <branch>"`. It writes the current counts even when one grew, adds new Java files named after the reason to the area (`--rebaseline home "merge of x" New.java`), and appends a `# Re-baselined <date>: <why> (File a -> b)` line to the tsv. Name the files and counts that grew in the commit message. A package never re-baselines; `--ratchet` refuses a count that grew.

## Contributing a translation

- Translate in the file with the same name as the English one, under your language's folder. Add only keys that exist in `values/`. Leave a text out rather than copying the English: a missing text falls back to English, and the completeness count stays honest.
- Keep every `%1$s` and `%2$d`. You may reorder them. Escape `'` as `\'`.
- Follow the glossary below. Ask in the pull request when a term does not fit.
- Run `python3 dm/tools/tests/test_android_i18n.py` before opening the pull request.
- No Weblate or Crowdin project is set up yet. The files are standard Android XML, so one can be connected later without changing them.
- A new language needs its `values-<qualifier>/` folder with all the area files, plus an entry in `Lang.TAGS` (with its name in `strings_settings.xml`) and in `LANGS` in `test_android_i18n.py`.
