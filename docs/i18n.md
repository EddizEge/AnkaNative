# Translating the Android launcher

The launcher (android/app) shows its texts in English, Turkish (tr), Brazilian Portuguese (pt-BR) and Latin American Spanish (es-419). English is the source and the fallback: a text a language lacks shows in English. This page is for engineers who move texts out of the Java and for translators.

Game logs, logcat lines, the readiness report and everything the Python packer or the native host prints stay English: users attach them to issues, and code parses some of them.

## Where texts live

All texts are Android string resources, one file per area:

| Folder | Language |
|---|---|
| `android/app/src/main/res/values/` | English (the source; `res/resources.properties` names it en-US) |
| `values-tr/` | Türkçe |
| `values-pt-rBR/` | Português (Brasil) |
| `values-b+es+419/` | Español (Latinoamérica). Android uses it for es-MX, es-AR, es-CO and the other Latin American Spanish locales. Spain's es-ES falls back to English. |

Each folder has the same files:

| File | Area | Java files |
|---|---|---|
| `strings_common.xml` | words used everywhere | closed while the areas are being moved: add the word to your own area instead |
| `strings_home.xml` | home | MainActivity, Ui, Prefs, FrontendLaunch |
| `strings_prepare.xml` | prepare | Ondevice, Job, PackService, DumpCheck |
| `strings_readiness.xml` | readiness | Readiness, ReadinessActivity, GameActivity's `readinessDialog` and `details` |
| `strings_game.xml` | game | GameActivity (the rest), SidePanel, TouchControls, Overlay, Fsr, Lsfg, SelftestActivity |
| `strings_saves.xml` | saves | SaveUi, SaveStore, SaveMigrate |
| `strings_packs.xml` | packs | PackUi, Pack, PackZip, PackFind, PackCheck, BuildCheck, DumpLayout, RomfsCheck, Nup, ShaderLibs, RewriteKey |
| `strings_settings.xml` | settings | GameSettings, Folders, GpuDriver, DriverFetch, DriverZip, Updater, UpdateCheck, ReleaseNotes, MemText, Signer, Profile, Lang |
| `strings_errors.xml` | errors | JobErrors: the packer's error codes |

Zstd, Native, Outputs, ShaderResults, LogProvider, PackEngine and FakeEngine keep their texts in English. They are failure details that reach the screen only after a translated sentence ("Cannot use X: *detail*").

## Keys

- A key is `<area>_<words>`, lower case, words joined by `_`: `home_access_title`, `prepare_cannot_use`, `settings_profile_update`. The first word is the file's area. `test_android_i18n.py` enforces both rules, so two areas can never add the same key.
- Name a key after what the text is, not after its English words: `saves_backup_done_title`, not `saves_saves_backed_up`. Then the English can change without renaming the key.
- A plural is a `<plurals>` resource with the same naming.
- Names that are never translated (the language names in their own language) get `translatable="false"` and live only in `values/`.
- Readiness requirement texts are `readiness_req_<fact>` and keep the form `title: why` in every language, because `Readiness.Req` splits on `": "`.

## Which call where

| Where the text is built | Call |
|---|---|
| A class with a Context (activities, Ui helpers, dialogs, PackService) | `c.getString(R.string.key)`, `c.getString(R.string.key, a, b)`, `c.getResources().getQuantityString(R.plurals.key, n, n)` |
| A class without Android (the JVM tests compile it on its own: BuildCheck, Pack, Profile, SaveStore, Readiness and the rest) | `Tr.s("key", args...)`, `Tr.p("key", n, args...)` |
| A text shown on the screen and also written to a log, a report or job.json | a `Msg`: `new Msg("key", args...)`, `Msg.plural("key", n, args...)`. The screen calls `msg.text()`, the report `msg.english()`. `toString()` is English. |
| An exception whose message the user should read in their language | `throw new LocalizedIOException("key", args...)`. `getMessage()` is English (logs, job.json, tests), `getLocalizedMessage()` is the user's language. |
| Showing any exception on the screen | `e.getLocalizedMessage()`, never `e.getMessage()`. For other exceptions it is the same text. |
| A log line, the readiness report, anything parsed back | English: `Tr.english("key", ...)`, `Tr.englishP(...)`, `msg.english()`, or a literal that stays English. Mark such a literal `// i18n-keep` when the ratchet counts it. |
| Dialog OK and Cancel buttons | `android.R.string.ok` and `android.R.string.cancel`. Android translates them, and the English is the same. |

`App` installs Tr's Android backend (`TrAndroid`) in every process (main, `:game`, `:selftest`, `:readiness`, `:pack`) before any provider, activity or service starts. On the JVM, `Tr` reads `values/strings_*.xml` from the folder the system property `nx.tr.res` names. Every JVM test passes `TR_RES` and compiles the `TR` sources (`Tr.java`, `Msg.java`, `LocalizedIOException.java`), so the English the tests see is the English the app shows.

A key that does not exist throws `MissingResourceException`. `test_android_i18n.py` checks that every key named in the Java (`Tr.*`, `Msg`, `LocalizedIOException`, `R.string`, `R.plurals`) exists in `values/`, with the right type.

### A missing key in a shipped build

The test suite is the guard, not the app. On the JVM and in a debuggable build (the test app, a debug build) a missing key, a format that does not fit its arguments or any other error of a text lookup through `Tr` or `Msg` throws, so developers and tests see it at once. A shipped (non-debuggable) build installs `Tr.Lenient` around `TrAndroid` (`App`, `Tr.forBuild`): it writes one error line to logcat naming the key and the error (`[RED] text string <key> (<language>): …`, once per key and language in a process), and shows the key's English instead, formatted; if that fails too, the English as written; if the key has no English at all, the key itself. That only keeps the user's screen alive: a text that hits it is a bug that `test_android_i18n.py` should have caught, so fix the text or the test. `TrJvmTest` covers this decision. `c.getString(R.string.x, …)` calls in classes with a Context do not go through `Tr`: a missing `R.string` id fails the build, but a bad format there still throws in every build, so only the placeholder checks of the test guard them.

## Writing a text

- **One resource per whole sentence.** Never glue fragments (`"Cannot use " + dir + ": " + why`). Write `Cannot use %1$s: %2$s`. Word order differs: Turkish puts the verb last ("%1$s kullanılamıyor: %2$s").
- **Positional arguments only:** `%1$s`, `%2$d`. A bare `%s` fails the test. Each translation uses exactly the same arguments as the English, in any order.
- **`%s` for anything that was concatenated before** (paths, names, doubles), and `%d` only for whole numbers. `%d` never groups digits (no `%,d` unless the English already had it), so English output stays the same.
- **A literal percent sign:** `%%` in a text that has arguments. A text without arguments is shown as written, so a lone `%` stays `%`.
- **No possessive after a runtime name.** Don't write `%1$s's save`. Turkish needs a suffix that depends on the name ("Zelda'nın", "Kong'un"), and Portuguese and Spanish reorder the phrase. Use a label form: `Save: %1$s`, or `Backing up the save of %1$s…`.
- **No case change of a translated text.** Never `toLowerCase` or `toUpperCase` a resource and put it inside a sentence. `Locale.ROOT` breaks Turkish İ and ı, and the other languages capitalize differently. Write a separate resource for the form you need.
- **Plurals for counts:** `<plurals>` with `one` and `other` in English (`other` is required). Turkish uses no plural after a number ("3 oyun"), so its `one` and `other` can be the same text. Pass the number twice when the text shows it: `getQuantityString(R.plurals.x, n, n)`, `Tr.p("x", n, n)`.
- **References to other labels** ("Settings › GPU driver", "Tap Retry") take the label from its own resource as an argument, so they match the translated button.
- **Numbers on screen:** `String.format(Locale.getDefault(), ...)`. Android's `getString` formats in the app's language. Logs and reports keep `Locale.ROOT`.
- **Escaping (aapt2):** write `'` as `\'` and `"` as `\"`, and a leading `@` or `?` as `\@` or `\?`. A newline is `\n`. Runs of spaces collapse to one unless the text is inside double quotes. Turkish uses `'` before suffixes ("shader\'lar", "Vulkan\'ı"). The test fails on an unescaped `'` or `"`.
- **Plain text only:** no `<b>`, `<xliff:g>` or other markup inside a string.
- **English output stays byte-identical** when a text moves. If you rephrase on purpose (a possessive, a plural that was wrong in English), list the changed English sentences in the commit message, so the docs and `docs/agents/symptoms.md` can follow.

## Language choice

Settings › Language offers System default, English, Türkçe, Português (Brasil) and Español (Latinoamérica) (`Lang.java`).

- **Android 13 and newer:** Android's per-app language (`LocaleManager`). It is the same setting as the system's Settings › Apps › Anka Native › Language. That page lists the languages from the localeConfig that the build generates (`generateLocaleConfig` in `build.gradle`, from `res/resources.properties` and the `values-*` folders). Android keeps the choice and applies it to every process of the app.
- **Android 12 (API 31, 32):** no per-app language, and the app has no AndroidX dependency (AppCompat would do the same through `AppCompatDelegate`). The choice is stored in `files/app_locale.txt`. Each activity and PackService wrap their context in it (`attachBaseContext` → `Lang.wrap`), and `TrAndroid` reads it. A process that is already running (a game, a Prepare job) keeps its language until it starts again.
- GameActivity and SelftestActivity list `locale|layoutDirection` in their `configChanges`, so a language change never restarts a running game. Their panels pick up the new language the next time they open. MainActivity and ReadinessActivity are recreated and draw themselves again.

**Pseudo-locales** are on in every build except the public release (`pseudoLocalesEnabled`). Turn on Developer options, then pick English (XA) (accented and longer) or ar-XB (right to left) as the phone's language. A text still hard-coded in the Java stays plain English, and a label that is too long gets cut.

## Tests

```sh
python3 dm/tools/tests/test_android_i18n.py                    # the rules, the ratchet, Tr on the JVM
python3 dm/tools/tests/test_android_i18n.py --list Ondevice.java   # what the ratchet still counts in a file, with line numbers
python3 dm/tools/tests/test_android_i18n.py --ratchet prepare      # write the area's current counts (it only goes down)
```

`test_android_i18n.py` checks:

- every strings file is well-formed XML;
- `values/` has exactly the `strings_<area>.xml` files, and each translation folder has the same ones;
- keys are named after their area;
- every key in a translation exists in the same English file;
- each string has the same arguments as its English;
- plurals have `other`;
- `'` and `"` are escaped;
- `translatable="false"` texts are not translated;
- readiness requirements keep `": "`;
- every key the Java names exists;
- every key is a string literal directly in the call (`Tr.s("key", ...)`, never `"readiness_req_" + fact`), so the check above sees it;
- Tr's XML backend matches aapt2 (TrJvmTest).

It prints each language's completeness without failing.

**The ratchet** (`dm/tools/tests/i18n_ratchet/<area>.tsv`) counts, per Java file, the literals that read as text shown to a user. A count may never grow. A file that is in no area's list must have none. When you move texts out of a file, run `--ratchet <area>` and commit the lower count. Lines that must stay English and that the counter still picks up (a report line, a technical name) get a `// i18n-keep` comment.

## Contributing a translation

- Translate in the file with the same name as the English one, under your language's folder. Add only keys that exist in `values/`. Leave a text out rather than copying the English: a missing text falls back to English, and the completeness count stays honest.
- Keep every `%1$s` and `%2$d`. You may reorder them. Escape `'` as `\'`.
- Follow the glossary below. Ask in the pull request when a term does not fit.
- Run `python3 dm/tools/tests/test_android_i18n.py` before opening the pull request.
- No Weblate or Crowdin project is set up yet. The files are standard Android XML, so one can be connected later without changing them.
- A new language needs its `values-<qualifier>/` folder with all the area files, plus an entry in `Lang.TAGS` (with its name in `strings_settings.xml`) and in `LANGS` in `test_android_i18n.py`.

## Glossary

- Product and technology names stay as they are: Anka Native, Vulkan, Turnip, Mesa, LSFG, Lossless Scaling, FSR, NVN, GitHub, Lossless.dll, title ID, build ID, `.nup`.
- "shader" stays untranslated in all three languages, as the emulator communities use it.
- Turkish: avoid suffixes on runtime names. When one is unavoidable, use the apostrophe form and escape it.
- Spanish: Latin American forms ("agregar", "archivo", "cuadros", "respaldo").
- Portuguese: Brazilian forms ("arquivo", "tela", "baixar").
